> 最后更新：2026-10-13

## 1. 这个软件要解决什么

Windows 用户的 C 盘（系统盘）会被各种软件和数据文件夹塞满，而机器上往往还有一块大容量
的空闲盘。用户想把这些文件夹搬到别的盘，但**直接剪切粘贴会让软件坏掉**——因为注册表、
快捷方式、服务、`%PATH%`、卸载信息里记的都是绝对路径。

本软件做三件事：

1. **扫描**：找出 C 盘上可以搬、需要小心、以及疑似残留可清理的文件夹，用界面列出来。
2. **搬家**：用户选中一个 → 弹出确认窗口 → 在目标盘建立同名文件夹 → 把内容搬过去 →
   **在原位置留下一个目录联接（junction）**，让软件继续照原路径工作。
3. **可撤销**：每一步都记账，随时能搬回来。

### 非目标（明确不做）

- ❌ **不适配 macOS / Linux**——本项目**只针对 Windows**。目录联接、Restart Manager、
  注册表卸载信息、MSIX、NTFS ACL 都是 Windows 独有机制，硬套到其他平台只会得到
  一个四不像。跨平台不在路线图上，也不会为"未来可能跨平台"付出抽象成本。
- ❌ 不做注册表清理、不做"垃圾清理大师"式的激进删除
- ❌ 不搬 Windows 系统自身、不搬商店应用（MSIX）
- ❌ 不提供"一键全搬"——**每个文件夹都必须用户单独确认**，因为这本质上是高风险操作
- ❌ 不保证 100% 的软件都能搬（见 §7 风险清单，有些软件天生抗拒）
- ❌ 不做静默埋点、不做后台上报（见 §14 反馈机制）

## 2. 可行性结论与影响分析

### 2.1 能做吗

**能做。** 这个需求在技术上属于成熟领域（同类工具有 Steam Mover、Link Shell Extension、
商业软件 Application Mover），核心手段是**目录联接**。我们不做黑魔法。

### 2.2 用了会有什么影响（必须如实告知用户，也要写进产品里）

**正面影响**

- C 盘释放空间，且软件**照常可用**（因为路径没变）。
- 卸载/重装仍然有效（安装程序看到的还是原路径）。
- 对软件本身透明，绝大多数程序察觉不到。

**代价与风险**

| 风险 | 说明 | 缓解 |
|---|---|---|
| **目标盘成为硬依赖** | 搬完之后 D 盘就是那个软件的命根子。D 盘拔了、坏了、盘符变了，软件立刻不可用 | 界面明确提示；检测可移动磁盘时拒绝搬入；盘符变化给出诊断 |
| **自动更新的软件可能出问题** | 有些更新器会删掉联接、或在原位置重建文件夹，导致"占了两份空间"或更新失败 | 归类为「需小心」，安装前告知；提供"搬回"一键撤销 |
| **反作弊/DRM 游戏可能拒绝启动** | 部分游戏校验自身路径真实性 | 归类为「需小心」，明确警告 |
| **备份软件可能重复计数** | 有些备份工具会跟随联接，把 D 盘数据当成 C 盘数据再备一份 | 文档说明；建议排除联接 |
| **性能差异** | 如果 D 盘是慢速机械盘而 C 盘是 NVMe，该软件启动会变慢 | 界面显示目标盘类型（SSD/HDD）供用户判断 |
| **杀毒软件误报** | "修改 Program Files + 创建联接"是典型可疑行为，很可能被拦或被 SmartScreen 警告 | 开源可审计；文档说明；后期可考虑代码签名 |
| **需要管理员权限** | 对 `Program Files`、`ProgramData` 操作必须提权 | 明确提权提示，不做静默提权 |
| **单盘机器用不了** | 只有一块盘时没有目标盘 | 扫描后直接告知，不提供无意义按钮 |
| **不是所有软件都验证过** | 我们只能保证"机制正确"，不能保证每个软件都兼容 | 三分归类 + 用户确认 + 可撤销，把决定权和退路都给用户 |

## 3. 核心技术方案：为什么必须是目录联接

**错误做法（用户直觉里的"搬家"）**：把 `C:\Program Files\Foo` 剪切到 `D:\Foo`。
结果：注册表、快捷方式、服务全指向 `C:\Program Files\Foo`，软件直接坏掉。

**正确做法**：

```
1. 复制   C:\Program Files\Foo  →  D:\Foo        （robocopy，保留 ACL 与时间戳）
2. 校验   D:\Foo 的文件数、总字节、抽样哈希与源一致
3. 删除   C:\Program Files\Foo                    （校验通过后才做）
4. 建联接 mklink /J "C:\Program Files\Foo" "D:\Foo"
5. 验证   通过联接读到 D 盘的文件，且路径仍显示为 C:\Program Files\Foo
```

目录联接（junction）是 NTFS 的**目录重解析点**，对应用程序完全透明：任何访问
`C:\Program Files\Foo\x.dll` 的代码都会被文件系统转到 `D:\Foo\x.dll`，而路径字符串不变。
这就是"软件察觉不到"的原理。

**为什么用联接（junction）而不是符号链接（symlink）**：联接是本地卷之间的目录重定向，
不需要开发者模式、不需要 `SeCreateSymbolicLinkPrivilege`，兼容性最好。符号链接更适合
文件级与跨机场景，本软件不需要。

**跨盘硬链接不成立**：Windows 的硬链接不能跨卷。如果被搬文件夹内部存在硬链接（见 §4.3），
复制会打断这种关系，因此这类文件夹我们**拒绝搬移**。

## 4. 判定规则（本软件的灵魂）

扫描结果分四类。**每一类判定都必须能追溯到具体证据**，界面上可展开查看"为什么这样判"。

### 4.1 禁止搬移（Forbidden）—— 硬黑名单

按**规范化后的真实路径**（先解析重解析点、统一大小写、去掉尾部分隔符）做前缀匹配。

**操作系统本体**

- `C:\Windows` 及其全部子目录（含 `WinSxS`、`System32`、`SysWOW64`、`assembly`、
  `servicing`、`Installer`、`Fonts`、`drivers`）
- `C:\$Recycle.Bin`、`C:\System Volume Information`、`C:\Recovery`、`C:\PerfLogs`
- `C:\MSOCache`、`C:\Config.Msi`、`C:\$WinREAgent`、`C:\$SysReset`
- 页面文件/休眠文件所在的系统卷关键项

**商店应用与系统组件（MSIX / 受保护 ACL）**

- `C:\Program Files\WindowsApps`
- `C:\Program Files\Windows Defender`、`C:\ProgramData\Microsoft\Windows Defender`
- `C:\Program Files\Windows NT`、`C:\Program Files\Common Files\microsoft shared`
- `C:\Program Files\dotnet`、`C:\Program Files (x86)\Microsoft.NET`
- `C:\Program Files\WindowsPowerShell`、`Windows Kits`
- `C:\Users\<用户>\AppData\Local\Packages`（UWP 应用数据，受 ACL 保护）
- `C:\Users\<用户>\AppData\Local\Microsoft\Windows\*`（系统外壳数据）
- `C:\Users\<用户>\AppData\Local\Temp`（系统临时目录）
- `C:\Users\<用户>\AppData\Local\Microsoft\WindowsApps`（商店应用别名）

**启动关键 / 驱动**

- 文件夹内含 `.sys` 驱动文件，且该驱动被 `HKLM\SYSTEM\CurrentControlSet\Services`
  登记为 `Start` ≤ 1（Boot/System 启动）→ 禁止
- 位于 EFI 系统分区、恢复分区上的任何内容

**技术前提不满足**

- 源卷或目标卷**不是 NTFS** → 无法建联接，禁止
- 被搬文件夹**本身已经是重解析点**（联接/符号链接）→ 禁止二次搬运
- 文件夹位于可移动磁盘、网络驱动器、内存盘 → 禁止作为目标
- 文件夹内存在**硬链接文件**（`NumberOfLinks > 1`）→ 禁止（见 §3）
- 文件夹是当前运行的程序自身所在目录 → 禁止（自毁保护）

### 4.1.1 云同步目录必须单独拦（实测发现的安全缺陷）

**现象**：`C:\Users\<用户>\OneDrive` 及其内部目录在 Windows 上属于「云文件占位符」。实测同一个目录：

| 观察者 | `File.GetAttributes` 结果 |
|---|---|
| PowerShell 5.1 | `1073`（**含** `ReparsePoint` 位） |
| 本程序（无清单） | `49`（不含） |
| 本程序（**已嵌入**声明 Windows 10 兼容性的应用清单） | `49`（仍然不含） |

并且本进程调用 `FSCTL_GET_REPARSE_POINT` 直接返回 `ERROR_NOT_A_REPARSE_POINT (4390)`。

**结论：Windows 对云占位符做进程级属性屏蔽，我们在本进程内无法把它识别成重解析点。**
（原本以为应用清单里的 `supportedOS` 声明能解开屏蔽，实测**不能**。）

若不管它，程序会把云同步目录当普通目录搬走 —— 复制占位文件会触发**全量下载**，
可能瞬间吃掉几十 GB 磁盘和带宽，甚至撑爆目标盘。这是本软件最危险的一类误操作。

**对策：不依赖那个被屏蔽的属性位，按「同步根」显式判定**，三条证据任一命中即禁止搬移：

1. **环境变量**：`OneDrive` / `OneDriveConsumer` / `OneDriveCommercial` / `Dropbox` / `GoogleDrive`
2. **注册表登记**：`HKCU\Software\Microsoft\OneDrive\Accounts\*\UserFolder`、
   `HKCU\Software\SyncEngines\Providers\*` 下的 `MountPoint`
3. **路径分段兜底**：路径中任何一段命中已知同步目录名（OneDrive、Dropbox、Google Drive、
   iCloud Drive、坚果云、百度网盘、阿里云盘、腾讯微云、MEGA、pCloud、Seafile、
   Nextcloud、ownCloud、Syncthing、微力同步 等）

第 3 条为何必要：同步根可能被移动、环境变量可能缺失、目录结构可能从别的机器拷来，
前两条都指望不上。代价是可能误报（无关文件夹恰好叫这些名字），
但**误报只损失一个可搬选项，漏报会触发全量下载** —— 两者代价不对称，故宁可误报。

**父目录同样要拦**：`C:\Users\<用户>` 内部装着同步根，搬它会连带搬走同步根，
因此降级为「可搬但需小心」并明确说明要先排除。

> 这一条是**在真实数据交叉验证中发现的**：PowerShell 引擎与 C# 内核在同一台机器上
> 对 `C:\Users\<用户名>\OneDrive` 给出了不同判定，追查下去才暴露了 Windows 的属性屏蔽行为。
> 如果只做单一实现的"自测"，这个缺陷会一直潜伏到用户真的点了"搬移"。

### 4.2 可以安全搬移（Safe）—— 典型目标

- 开发工具链与缓存：`.npm`、`.gradle`、`.m2`、`.cargo`、`.nuget`、`pip` 缓存、
  `AppData\Local\JetBrains`、`AppData\Local\Android\Sdk`、`.vscode\extensions`
- 软件数据目录：`AppData\Local\<App>`、`AppData\Roaming\<App>`（纯数据、无服务）
- 游戏与启动器自建目录（Steam 库、Epic 库、独立游戏目录）
- 便携软件（免安装、无注册表依赖）
- 大型缓存在 `ProgramData` 下且对应软件无服务的
- 用户文档类：`Downloads`、`Documents` 等 —— **但优先引导用户用 Windows 自带的
  「属性 → 位置」迁移**（更标准、系统知道这件事），联接作为备选

判定依据：位于允许根目录内、非重解析点、无服务依赖、无驱动、未被本次运行占用、
注册表卸载项存在或明确属于数据目录。

### 4.3 可以搬但需小心（Caution）—— 需要额外确认与前置动作

- `Program Files` 下的一般已安装软件（需提权、需先退出该软件、需先停其服务）
- 带**自动更新器**的软件（Chrome、Edge、各类 Electron 应用）—— 更新器可能破坏联接
- 带**反作弊**的游戏（EasyAntiCheat、BattlEye、部分国产网游）
- **当前正在运行**的软件（文件被占用，必须先关闭）
- 注册了 **Windows 服务**的软件（搬前需停服务，搬后需验证服务能起来）
- 注册了 **COM 组件 / App Paths / 文件关联**的软件（联接理论上可保路径，但需回归测试）
- `C:\ProgramData\<App>` 下带服务或带计划任务的软件

这类在界面上用醒目颜色标注，确认窗口里必须列出**具体风险点**与**前置动作清单**。

### 4.4 疑似残留，建议清理（Junk Candidate）—— 只报告，绝不自动删

判定需要**多条证据同时成立**，任一存疑即降级为"未知，不动"：

- 位于 `Program Files` / `ProgramData` / `AppData\Local` 下
- 在三个卸载注册表位置中**都找不到**对应条目（按名称、`InstallLocation`、发布者模糊匹配）
- 且**超过 180 天未修改**
- 且目录内无可执行文件被登记为服务/计划任务
- 或命名特征明显：`xxx (1)`、`xxx_old`、`xxx.bak`、`backup`、`temp`、`新建文件夹`
- 或为空目录

**清理动作永远是**：先移到回收站（可还原），并写入撤销日志，
界面上写明"这是推测，请你确认后才会执行"。绝不静默删除。

## 5. 权限模型

| 场景 | 所需权限 | 说明 |
|---|---|---|
| 扫描（只读） | 普通用户 | 部分路径（如 `WindowsApps`）读不到，标注"权限不足，已跳过" |
| 搬移用户目录（`AppData`、用户文件夹） | 普通用户 | 大多数搬移场景其实不需要管理员 |
| 搬移 `Program Files` / `ProgramData` | **管理员** | 建联接、删原目录都在受保护位置 |
| 停/起服务 | **管理员** | 搬带服务的软件前置 |
| 写入程序所在盘以外的盘 | 普通用户 | 目标盘需有写权限 |

**策略**：程序清单里声明 `requireAdministrator`，启动即提权，避免"扫到一半发现权限不够"
的割裂体验。启动时明确告知用户"本程序需要管理员权限，因为它要修改 Program Files"。

**长路径**：超过 260 字符的路径需要 `\\?\` 前缀处理；文档要求用户开启
`LongPathsEnabled`（或程序内部全程使用 `\\?\`）。

**批处理/安装脚本**：不使用 `cmd /c mklink`（有转义与注入风险），改用
`DeviceIoControl(FSCTL_SET_REPARSE_POINT)` 或 `CreateSymbolicLink` API 直接创建。

## 6. 多磁盘处理

1. 枚举所有**固定、NTFS、非只读**的卷（排除源卷）。
2. 界面列出：盘符、卷标、文件系统、总容量、剩余容量、**介质类型（SSD/HDD）**。
3. 用户选目标盘，或为每个文件夹单独指定。
4. 前置校验：
   - 目标卷必须是 NTFS 固定磁盘（可移动/网络/FAT32/exFAT → 直接拒绝并说明原因）
   - 剩余空间 ≥ 待搬大小 × 1.15（留出元数据与校验余量）
   - 目标路径不能已存在同名非空文件夹（要么改名，要么让用户确认合并策略——默认拒绝）
5. 若机器只有一块盘 → 扫描后直接提示"没有可用的目标盘"，不显示搬移按钮。

## 7. 迁移流程状态机与失败处理

> **实现后的改进（v0.1）**：初版设计是「复制 → 校验 → **删除源** → 建联接」。
> 实现时发现这条路有个不可接受的窗口：删除源目录是**不可逆**的，而建联接可能失败
> （权限、目标被占、磁盘错误）。一旦先删后建失败，用户就得到一个「软件已经没了、
> 原位置也是空的」的烂摊子。
>
> 实际实现改用**「改名让位」换出回滚窗口**，把不可逆步骤夹在两个可逆步骤之间：

```
[空闲]
  → 预检 Preflight（只读，不改动任何东西）
       · 路径黑名单 / 共享组件 / 云同步目录复核（按真实路径）
       · 是否重解析点      · 硬链接检测（硬链接不能跨卷）
       · 目标卷资格（NTFS + 固定磁盘）与剩余空间（含 5% 余量）
       · 占用检测（Restart Manager 查哪些进程正打开其中的文件）
       · 是否需要管理员权限
  → 用户确认（确认窗口展示全部风险、阻止项与前置动作）
  → 复制 Copy          robocopy /E /COPY:DATS /DCOPY:DAT /R:1 /W:1
                       保留 ACL 失败时自动降级为 /COPY:DAT 重试
                       退出码 ≥ 8 → 清理目标副本，源目录分毫未动，结束
  → 校验 Verify        文件数 + 总字节 + 抽样哈希（取最大的若干个文件）
                       不一致 → 清理目标副本，源目录分毫未动，结束
  → 改名让位 Rename    源目录改名成 <源>.appmover-old-<记录号>
                       （同卷改名是元数据操作，瞬间完成且可逆）
  → 建联接 Link        FSCTL_SET_REPARSE_POINT（不经过 cmd /c mklink，避免注入与转义）
  → 验证联接 VerifyLink  解析真实路径必须等于目标；再通过联接读取一个哨兵文件
  → 删旧 Cleanup       删除改名后的旧目录（此时数据已在目标盘且联接已生效）
  → 记账 Journal       写入撤销日志
  → [完成]
```

**失败即回滚，且不存在"同时失去两份数据"的时刻**：

| 失败位置 | 磁盘状态 | 处理 |
|---|---|---|
| 复制 / 校验 | 源完好，目标有半截副本 | 删除目标副本，源目录未动 |
| 改名 | 源完好 | 无需处理，直接报错 |
| 建联接 / 验证联接 | 源已改名，数据完好 | 拆除可能已建的联接 → 把改名后的目录**改回原名** → 清理目标副本 |
| 删旧目录 | 目标数据 + 联接都正常 | 删除失败**不算搬移失败**，只提示残留路径（多占一份空间，功能不受影响） |

**撤销（Undo）**同样遵循"先确保有可用副本再删"：

```
严格前置检查（联接是否存在、是否指向记录里的目标）→ 不符就拒绝，绝不猜测
  → 拆除联接
  → 把目标数据复制回原位置
  → 校验
  → 删除目标盘上的副本
     （失败则重建联接，恢复到撤销前的可用状态）
```

**占用检测**用 Windows 的 Restart Manager（`RmStartSession` / `RmRegisterResources` /
`RmGetList`）——这是 Windows 安装程序的标准做法，比自己枚举句柄更可靠，还能给出服务名。

**占用检测**：用 `RestartManager` API（`RmStartSession` / `RmRegisterResources`）查询
哪些进程正在使用目标文件夹内的文件——这比枚举句柄可靠得多，也是 Windows 安装程序的标准做法。

## 8. 撤销机制

每次搬移写入一条日志（`journal.json` + 人类可读的 `journal.log`）：

```json
{
  "id": "20261013-091500-001",
  "time": "2026-10-13T09:15:00+08:00",
  "original": "C:\\Program Files\\Foo",
  "target": "D:\\Foo",
  "bytes": 1234567890,
  "files": 4321,
  "junctionCreated": true,
  "verification": { "filesMatch": true, "bytesMatch": true, "hashSamples": 12 },
  "status": "completed"
}
```

**撤销流程**：删除联接 → 把 `D:\Foo` 搬回 `C:\Program Files\Foo` → 校验 → 删除目标残留
→ 日志标记 `reverted`。全程同样遵循"复制-校验-删除"。

界面提供"历史记录"页，可逐条撤销。**这是本软件敢让用户动手的底气**。

## 9. 技术栈选择

**环境实测**：本机有 .NET 8 **运行时**（无 SDK）、Node.js、Git；
Windows 自带 .NET Framework 4.8 的 `csc.exe`（C# 5 语法上限）。

**决策：C# + WinForms + .NET Framework 4.8，用系统自带 `csc.exe` 编译。**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **C# WinForms / .NET Framework 4.8** | **零安装**（用系统自带编译器）；产物约 200 KB；Win10/11 开箱即用；原生 API 调用方便（重解析点、RestartManager） | 语法限于 C# 5（无字符串插值、无 `?.`） | ✅ **采用** |
| .NET 8 WPF 自包含 | 现代语法、UI 更强 | 需装 SDK；自包含产物约 150 MB；发布体积对用户不友好 | ❌ 备选 |
| PowerShell + WPF | 零安装、开发快 | 易被误杀、分发不专业、权限与签名更麻烦 | ❌ |
| Electron / Tauri | UI 漂亮 | 体积巨大、需要额外工具链、与系统 API 交互更绕 | ❌ |

**理由**：本软件的价值在于**系统级操作的可靠性**，不在于 UI 炫技。一个 200 KB、
不依赖任何运行时安装的 exe，是这个场景最优的分发形态。

## 10. 界面设计（三页）

1. **扫描页**：目标盘选择 + 「开始扫描」；结果表格列出：名称、路径、大小、文件数、
   分类徽章（可搬/需小心/禁止/疑似残留）、判定理由（可展开）。
   排序、筛选（只看可搬）、搜索。
2. **确认窗口**：显示源路径、目标路径、大小、目标盘剩余空间变化、
   **风险点列表**、**前置动作清单**（需先关闭的进程/需停的服务）、
   勾选"我已阅读并确认"。危险项需二次输入确认。
3. **历史/撤销页**：搬移记录、状态、一键撤销、日志导出。

另设 **干跑模式（Dry Run）**：只出计划不动文件，供用户先看一遍。

## 11. 测试计划

- **单元测试**：路径规范化与黑名单匹配（含大小写、尾斜杠、`..`、重解析点绕过等对抗用例）
- **规则测试**：三类判定的证据链（构造假的注册表/目录结构）
- **集成测试**（在虚拟机或专用测试目录）：
  - 正常搬移 + 软件仍可用（用便携程序做哨兵）
  - 复制作业中途失败 → 源目录完好
  - 校验不通过 → 自动清理目标，源目录完好
  - 文件被占用 → 正确报出占用进程
  - 目标盘空间不足 → 拒绝并说明
  - 撤销 → 完整还原
  - **反向测试**：尝试搬 `C:\Windows`、`WindowsApps`、已联接目录 → 必须被拒
- **手工验收矩阵**：在干净 Win10 / Win11 各跑一遍，覆盖单盘、双盘、可移动盘场景

## 14. 反馈机制

设计细节见 [FEEDBACK.md](FEEDBACK.md)，此处只记要点：

- **不建自建后端**：用 GitHub Issues 当接收端，零运维、零成本、公开可追踪、用户无需额外注册。
- **三条入口**：程序内 `feedback` 命令生成预填链接；静态页 `docs/feedback.html`（可托管 GitHub Pages）；
  用户直接在仓库开 issue。
- **主要采集对象**：判定引擎给出 `low` 置信度的目录名，以及被判为「疑似残留」的项。
  这些正是规则最需要补的地方。
- **脱敏**：用户名 → `<user>`，计算机名 → `<PC>`；只上传目录名/路径/判定依据/环境版本，
  **绝不读取或上传文件内容**；报告末尾明写这一点。
- **闭环**：反馈 → 补规则 → **同时在 `SelfTest.cs` 加回归用例** → 跑 selftest 全绿才算改完。
  反馈不只用来"改一次"，而是固化成测试，防止同一个误判在后续重构中复发。
  已经有一批用例来自这个闭环（`Program Files (x86)\WindowsPowerShell`、
  `Common Files`、`NVIDIA Corporation`、剪映/微信/游戏存档、OneDrive 云同步、
  `SoftwareDistribution`、`boost_interprocess`、`ProgramData\Packages`）。

**明确不做**：静默埋点、后台上报。任何信息上传都必须由用户主动点击提交。
