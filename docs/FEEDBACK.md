# 反馈机制设计

> 目标：**在没有自建服务器、没有预算、没有运维的前提下，把用户遇到的"没见过的目录名"和报错收回来**，
> 并且让这些反馈能被长期追踪、能被直接转化为规则改进。

---

## 1. 为什么不用自建后端

| 方案 | 问题 |
|---|---|
| 自建 API + 数据库 | 需要服务器、域名、HTTPS、运维、费用；停服即丢反馈；还要自己处理隐私合规 |
| 第三方表单服务 | 依赖第三方存活；免费额度有限；数据在别人手里；还要注册账号 |
| 邮件收集 | 无法公开追踪，无法协作，容易漏 |
| **GitHub Issues** | ✅ 零成本、零运维、公开可追踪、自带搜索与标签、用户无需额外注册、长期可归档 |

结论：**用 GitHub Issues 当后端**。这不是妥协，而是这个规模的开源工具最合适的形态。

---

## 2. 三种反馈入口

### 入口一：程序内一键生成（推荐）

程序遇到**把握不大的判定**时会主动提示，也可以随时手动运行：

```
AppMover.exe feedback --path "C:\某个目录" --open     # 判定问题
AppMover.exe feedback --error "报错原文" --open        # 运行报错
AppMover.exe feedback --unknown                       # 批量收集"规则没见过"的目录名
```

程序会：
1. 采集诊断信息并**脱敏**
2. 在自己目录下写出 `feedback\feedback-<时间戳>.md` 和 `.json`（本地留档）
3. 打印一个**预先填好标题/正文/标签**的 GitHub 新建 issue 链接；加 `--open` 直接打开浏览器

用户点开、看一眼、提交。全程不需要注册任何账号。

### 入口二：静态网页（`docs/feedback.html`）

一个不依赖后端的单页应用，可直接托管在 **GitHub Pages**：

- 把程序生成的报告内容粘贴进去 → 生成同样的预填提交链接
- 支持 `?repo=owner/name` 参数指定仓库，因此换仓库不用改代码
- 页面本身**不收集也不上传任何数据**，只是拼一个链接

### 入口三：直接在仓库开 issue

仓库提供 issue 模板，用户自己写也行。

## 3. 脱敏规则（必须明确、可审计）

程序生成的报告**只包含**：

| 采集项 | 用途 |
|---|---|
| 程序版本 | 定位是哪个版本的问题 |
| Windows 版本、x64/x86 | 复现环境 |
| 是否管理员 | 判断是否权限问题 |
| 磁盘列表（盘符/文件系统/类型/可用空间） | 判断目标盘资格相关的问题 |
| 出问题的路径 | 定位规则 |
| 判定结果与依据 | 规则为什么这么判 |
| 把握不大的目录名清单 | **改进规则最需要的数据** |
| 报错原文 | 定位缺陷 |

**替换规则**：

- `C:\Users\<真实用户名>` → `C:\Users\<user>`
- 计算机名 → `<PC>`
- 目录名本身**保留**（那正是需要分析的信息）

**绝不包含**：文件内容、账号密码密钥、真实用户名、真实计算机名。报告末尾会写明这一点。

---

## 4. "没见过的目录名"是怎么收集的

判定引擎对每个目录给出**置信度**。凡是 `low` 置信度（例如
「Program Files 下但注册表无对应卸载项，可能是共享组件或绿色软件，也可能是卸载残留」）
以及被判为「疑似残留」的项，都会被 `feedback --unknown` 收集进报告。

这条链路的闭环是：

```
用户跑 feedback --unknown
      ↓
报告里出现一批"规则拿不准"的目录名
      ↓
维护者据此判断：是规则缺失，还是本该判成别的类别
      ↓
改 Classifier 规则表
      ↓
**同时在 SelfTest.cs 里加一条对应用例**（用真实目录名，不用构造字符串）
      ↓
跑 selftest，全绿才算改完
```

最后一步是关键：反馈不只用来"改一次"，而是固化成回归测试，
避免同一个误判在后续重构中复发。项目里已经有一批这样的用例
（`Program Files (x86)\WindowsPowerShell` 无空格、`Common Files`、`NVIDIA Corporation`、
剪映/微信/游戏存档、OneDrive 云同步目录等）。

## 5. 维护者需要做的配置

反馈链接里的仓库地址有一处需要配置（当前是占位符 `REPLACE-ME/AppMover`）：

**方式 A（推荐，不用重新编译）**：在 `AppMover.exe` 同目录放 `feedback.json`：

```json
{ "repo": "你的用户名/AppMover" }
```

**方式 B**：修改 `src/AppMover/Core/Feedback.cs` 里的 `DefaultRepo` 常量后重新编译。

程序在检测到仓库未配置时，会明确提示用户"链接中的 REPLACE-ME 需要替换"，
不会静默生成一个无效链接。

## 6. 仓库侧建议

- 建两个标签：`feedback`（所有反馈入口自动带上）、`rule-gap`（规则缺失/误判）
- 配 issue 模板，把「正确的判断应该是什么」作为必填项 ——
  光说"判错了"无法改进规则，必须知道正确答案
- 定期把已修复的反馈关掉并注明对应的测试用例名，形成可追溯的改进历史

---

## 7. 明确不做的事

- ❌ **不**做静默埋点、**不**后台上报。任何信息上传都必须由用户主动点击提交。
- ❌ **不**做 macOS / Linux 适配。本项目只针对 Windows。
- ❌ 不为了"收集更多数据"而扩大采集范围。能改规则所需的最小信息就是目录名 + 判定依据。
