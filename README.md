# 软件搬家 · AppMover

把 C 盘上的软件和数据文件夹安全搬到其他磁盘，**让软件照常能用**。

> 状态：**M3 界面完成**——已产出可双击使用的图形界面程序。累计 123 项自动化验证全绿
> （命令行回归 86 + 界面冒烟 37），已与独立的 PowerShell 引擎在真实数据上交叉验证。
> 下一步是 M4：中英 README、LICENSE、GitHub Actions 自动出 Release。
>
> **平台：仅 Windows。** 不做 macOS / Linux 适配——目录联接、Restart Manager、注册表卸载信息、
> NTFS ACL 都是 Windows 独有机制，跨平台不在路线图上。

## 怎么用

**普通用户**：双击 `build\AppMover.exe`

1. 选目标盘（默认自动选空闲最大的非系统盘）
2. 点「开始扫描」，等它列出 C 盘上的目录（每项都带分类和判定依据）
3. 选中一项 → 点「搬移选中项」（或双击）→ 在确认窗口里看清风险和前置动作 → 勾选确认 → 开始
4. 出问题就在「历史记录与撤销」页一键撤销

**进阶用户 / 排错**：`build\AppMover-cli.exe`，命令见下方「验证」。

> 为什么不合成一个 exe：WinExe 子系统不会附加到父进程的控制台，命令行输出会全部丢失；
> 要在一个二进制里兼顾两者得手工 AttachConsole + 重开 stdout，既脆弱又难测。
> 两个可执行文件共享同一份 Core，是这个场景更稳妥的做法。

## 它解决什么问题

C 盘（系统盘）被各种软件和数据塞满，而机器上往往还有一块空盘。
直接剪切粘贴会让软件坏掉——注册表、快捷方式、服务、`%PATH%`、卸载信息里
记的都是绝对路径。本软件的做法是：

```
复制到目标盘  →  校验一致  →  删除原目录  →  在原位置建立「目录联接」
```

目录联接（junction）对软件完全透明：访问 `C:\Program Files\Foo\x.dll` 的代码
会被文件系统转到 `D:\Foo\x.dll`，而**路径字符串没有任何变化**。
这就是"搬完还能用"的原理。

## 三类判定 + 一类清理建议

软件在扫描时会给出分类，并**展示判定依据**，而不是丢一个结论给你：

| 分类 | 含义 | 本机实测 |
|---|---|---|
| 🟢 可安全搬移 | 数据目录、缓存、便携软件 | 134 项 / 31.61 GB |
| 🟠 可搬但需小心 | Program Files 下的已安装软件、含服务的、有自动更新器的 | 70 项 / 15.33 GB |
| 🔴 禁止搬移 | Windows 本体、共享组件、驱动、商店应用、卸载信息 | 73 项 / 33.28 GB |
| 🟣 疑似残留可清理 | 缓存与安装器残留，**只建议，绝不自动删** | 11 项 / 2.53 GB |

## 规则是怎么定出来的（不是拍脑袋）

先在真实机器上跑扫描（`tools/scan-inventory.ps1`），再用判定引擎
（`tools/make-report.ps1`）分类，然后**逐条人工审计输出**。
审计发现并修正了三类系统性误判：

1. **把共享组件当垃圾** —— `Common Files`、`NVIDIA Corporation` 这类目录没有
   卸载登记项，但被多个软件/驱动引用。→ 新增「共享组件/厂商目录」独立黑名单。
2. **把正在使用的软件数据当垃圾** —— 剪映 6.49 GB、微信 3.52 GB、米哈游、
   博德之门存档等被判成残留。根因是**「注册表无卸载项」对 AppData 目录是极弱信号**
   （绝大多数软件的数据目录本来就不登记）。→ 重写规则：AppData 只区分「缓存 / 数据」，
   绝不以无卸载项推断残留。误判从 18.45 GB 降到 2.53 GB。
3. **路径大小写/空格假设错误** —— 真实目录名是 `WindowsPowerShell`（无空格），
   规则却按 `Windows PowerShell` 写，导致 32 位系统目录漏网。
   → 教训：**回归测试必须用真实路径，不能用与正则同构的构造字符串**。

这就是「严谨」的具体含义：**每个判定都要有证据，且规则要用真实数据反复审计**。

## 安全底线

- 校验未通过前**绝不删除**源目录；任何一步失败都回到"原目录可用"
- 每个文件夹**必须用户单独确认**，没有"一键全搬"
- 全程写撤销日志，**随时可搬回**
- 提供**干跑模式**：只出计划，不动文件
- 硬黑名单按规范化真实路径匹配（解析联接、统一大小写），防绕过

## 技术栈

**C# + WinForms + .NET Framework 4.8，用系统自带 `csc.exe` 编译。**

选它的理由：**零安装**。产物约 200 KB，Windows 10/11 开箱即用，
不需要用户装任何运行时。本软件的价值在系统级操作的可靠性，不在 UI 炫技。

代价：语法上限 C# 5（无字符串插值、无 `?.`），已在编码规范中接受。

## 反馈机制：不用自建服务器也能收到反馈

这个软件是便携工具，**不连接任何自建后端**。反馈通过 GitHub Issue 收集：

```
AppMover.exe feedback --path "C:\某个目录" --open    # 报告一次误判
AppMover.exe feedback --error "报错原文" --open       # 报告一个缺陷
AppMover.exe feedback --unknown                      # 批量收集"规则没见过"的目录名
```

程序会生成一份**已脱敏**的诊断报告（本地留档），并给出一个**预先填好标题/正文/标签**的
GitHub 新建 issue 链接——用户点开、过目、提交即可。另有静态反馈页 `docs/feedback.html`，
可直接托管到 GitHub Pages。

**脱敏规则**：路径里的用户名 → `<user>`，计算机名 → `<PC>`；**只上传目录名/路径/判定依据/
环境版本，绝不读取或上传任何文件内容**。

这条链路已经跑通并产生了实际收益：一次 `feedback --unknown` 收集到 35 条"规则拿不准"的目录，
据此发现 `C:\ProgramData\SoftwareDistribution`（Windows 更新缓存）、`boost_interprocess`
（运行中程序的共享内存）、`ProgramData\Packages`（商店数据）都被错误地当成了普通应用数据，
补进规则并**固化为回归用例**。详见 [docs/FEEDBACK.md](docs/FEEDBACK.md)。

## 已验证的内容

```
# 构建（不需要 .NET SDK，用系统自带编译器）
powershell -ExecutionPolicy Bypass -File src\build.ps1                 # 出两个 exe
powershell -ExecutionPolicy Bypass -File src\build.ps1 -Run selftest  # 内核回归 86 项
powershell -ExecutionPolicy Bypass -File src\build.ps1 -SmokeUi       # 界面冒烟 37 项

# 命令行工具
build\AppMover-cli.exe volumes        # 枚举卷并判断能否作为搬移目标
build\AppMover-cli.exe classify <路径> # 单个目录的分类与判定依据
build\AppMover-cli.exe plan <路径>     # 规划一次搬移（只读，含占用检测）
build\AppMover-cli.exe move <路径>     # 执行搬移
build\AppMover-cli.exe journal        # 搬移记录
build\AppMover-cli.exe undo <记录号>   # 撤销
build\AppMover-cli.exe feedback       # 生成脱敏诊断报告
```

### 界面怎么在没有人工看画面的情况下验证

WinForms 有一类错误只在真正布局时才暴露（停靠顺序写反导致控件被覆盖、
在父容器尺寸为 0 时算锚定偏移导致按钮跑到窗口外），编译期发现不了。
所以程序带一个无头冒烟模式：`AppMover.exe --smoke <报告文件>`，
它会真的 `Show()` 窗口，然后对**控件的实际几何边界**做断言：

- 关键控件必须完全落在父容器客户区内
- 顶部工具条不能与结果区域重叠（`工具条底部 76 <= 结果区域顶部 76`）
- 对话框按钮不能超出窗口
- 有阻止项时「开始搬移」必须是禁用状态

这个断言经过**变异测试**验证有效：把停靠顺序改回错误写法后，
测试立刻报 `结果区域顶部 0`（被工具条盖住 76 px）并失败。

回归测试里**每一条都对应一个真实踩过的坑**，包括：

| 测试组 | 防止重现的问题 |
|---|---|
| 前缀陷阱 | `C:\WindowsOld` 被误认为在 `C:\Windows` 之下 |
| 禁止搬移 | `Program Files (x86)\WindowsPowerShell`（**无空格**）曾因路径假设错误漏网 |
| 共享组件 | `Common Files`、`NVIDIA Corporation` 曾被误判成"垃圾" |
| AppData 不是垃圾 | 剪映、微信、米哈游、游戏存档曾被误判成"残留" |
| 云同步目录 | OneDrive 的重解析点属性被 Windows 屏蔽，漏判会触发云端**全量下载** |
| 联接往返 | 删除联接**绝不能**连带删除目标数据 |
| 完整搬移+撤销 | 端到端跑一遍，校验哈希、联接指向、数据只有一份 |
| 界面几何 | 停靠顺序、按钮越界、阻止项下的按钮禁用状态 |

## 交叉验证

同一台机器上，用两个**独立实现**（`tools/make-report.ps1` 的 PowerShell 引擎、
`src/` 的 C# 内核）分别扫描并分类，逐条比对：

- 条目数 288 vs 287（唯一差异是刻意跳过的系统目录 `OneDriveTemp`）
- 分类分歧 2 项，均为 C# 更严格（统计不完整时降级、云同步目录名拦截）

**云同步那个安全缺陷就是靠这个交叉验证发现的** —— 单一实现的自测永远不会暴露它。
